## Q5. What generates `__amd_rocclr_copyBuffer` in a ggml HIP graph

HIP maps `cudaMemcpyAsync` → `hipMemcpyAsync`. ROCClr implements that as the blit `__amd_rocclr_copyBuffer`. `cudaMemcpy2DAsync` is usually `__amd_rocclr_copyBufferRect`, **not** `copyBuffer`. Count both names or you will mis-classify the 2D path. `cudaMemsetAsync` is `fillBuffer`, not a copy. `hipMalloc` / pool grow is not a copy.

On a single-GPU HIP run, **scheduler splits are almost certainly not the 1.25M**. slaren: with one GPU there is one copy slot (`ggml-org/llama.cpp` discussion 10949). Ember’s 602 copyBuffer/token vs 582 `quantize_q8_1`/token is a 1.03:1 pairing. That is the mul_mat src1 materialize-then-quantize loop, not graph-split H2D.

### 1. Non-contiguous src1 (and src0) inside `ggml_cuda_op_mul_mat` — primary suspect

`engine/ggml/src/ggml-cuda/ggml-cuda.cu:1478-1510` `ggml_cuda_cpy_tensor_2d`, called at 1965-1967 (src1) and 1979-1981 (src0).

Triggered when `src1_on_device && !src1_is_contiguous` (1965). Contiguous src1 skips the copy and quantizes in place (1874-1879).

Three HIP implementations, all D2D:

| layout | API | rocprof name | size |
|---|---|---|---|
| packed (`nb0==ts && nb1==ts*ne0/bs`) | `cudaMemcpyAsync` | `copyBuffer` | `i1_diff * nb1` bytes |
| row-contiguous (`nb0==ts`) | `cudaMemcpy2DAsync` | **`copyBufferRect`** | width `ts*ne0/bs`, height `i1_diff` |
| element-strided | `cudaMemcpy2DAsync` **per row** | `copyBufferRect` × `i1_diff` | width `ts/bs`, height `ne0` |

**Trace ID:** same compute stream as the following `quantize_q8_1` (`ctx.stream(id, is)`, usually stream 0). Size for a 2560-f32 activation column: 10240 B unpadded; padded width `GGML_PAD(ne10, 512)*4` (`MATRIX_ROW_PADDING` in `common.cuh:133`). If you see 10240 B `copyBuffer` then `quantize_q8_1` then `mul_mat_vec_q`, that is this path. If the name is `copyBufferRect`, it is the 2D branch of the same function — still this mechanism, just not in the 1.25M `copyBuffer` counter.

Per-token 1:1 with quantize means src1 is a **view** (RMS out, HC mix, reshape) almost every mul_mat. Making src1 contiguous in the graph (one `ggml_cont` per shared activation, then many mul_mats) collapses N copies to 1.

### 2. `GGML_OP_CONT` / `DUP` / `CPY` nodes

`ggml-cuda.cu:2854-2861`: CONT and DUP call `ggml_cuda_dup` → `ggml_cuda_cpy` (`cpy.cu:595-638`).

- Same type **and** both contiguous: `cudaMemcpyAsync` → **`copyBuffer`**, size `ggml_nbytes(src0)`, compute stream.
- Else: `cpy_*` **kernels** (not copyBuffer). Transposed/permuted CONT is a kernel, not a blit.

This tree inserts a lot of `ggml_cont` on the Qwen/HC path (`deepseek4_graph.cpp` ~456–2856: views after transpose, HC state, residual). Those only become `copyBuffer` when the dest is packed. **Trace ID:** kernel name still `copyBuffer` but **no** following `quantize_q8_1`; adjacent ops are `rms_norm` / `add` / `mul` / `transpose`. Size = full tensor nbytes (HC state 4×2560×4 = 40960 B, or 2560×q×4 for a hidden).

llama.cpp b9827 / PR 25057 added a `cudaMemcpy2DAsync` fast path inside `ggml_cuda_cpy` for strided same-type copies (GDN snapshot slots). That would show as `copyBufferRect`. Check whether this fork has that commit; current `cpy.cu:630` is still the contiguous-only memcpy.

### 3. `ggml_backend_sched` splits → `ggml_backend_tensor_copy`

`ggml-backend.cpp:1050` `ggml_backend_sched_split_graph` (new split when backend_id changes or weights on an incompatible backend, 1337-1351). Copies created as `"4.cpy"` (1391-1398). Executed in `ggml_backend_sched_compute_splits` 1583-1701.

HIP implementation:

- Preferred: `ggml_backend_cuda_cpy_tensor_async` (`ggml-cuda.cu:3255-3307`) `cudaMemcpyAsync` on **`ctx.stream()`**, no device-wide sync.
- Fallback: `ggml_backend_cuda_buffer_cpy_tensor` (`922-937`) `cudaMemcpyAsync` on **`cudaStreamPerThread` then `cudaStreamSynchronize`**. That is host-blocking and will show as idle gaps in the GPU timeline.

**Trace ID:** `copyBuffer` of **weight** size (expert `nb[2]`, not 10 KiB), often on a different stream than compute, possibly with a following host sync gap. `GGML_SCHED_DEBUG=1` prints split inputs (discussion 10182, slaren). On GPU-only Ember this count should be ~0 per token. If it is not, something is bouncing CPU↔HIP every layer (unsupported op).

Selective MoE weight copy (1605-1689) is H2D of used experts only (`tensor_set_async` + 512 B padding). Trace: H2D `copyBuffer` sized `n_used * expert_nb[2]`, not D2D 10 KiB.

### 4. Padding / alignment — mostly **not** copyBuffer

`ggml-cuda.cu:1846-1858`: non-contiguous src0 gets a pool buffer **memset to 0**, then `cpy_tensor_2d`. The memset is `fillBuffer`. The copy is mechanism 1.

Quantized compute-buffer tail pad (1853-1858) is also memset.

`MATRIX_ROW_PADDING=512` inflates the **quantize output** and the packed-copy width; it does not add extra copy launches by itself.

### 5. Pool reallocation — **not** copyBuffer

`ggml_cuda_pool_leg` / VMM pool: `cudaMalloc` / `cuMemMap`. No blit of live tensors. A pool grow does not explain 1.25M launches.

### 6. Concat / argsort / top-k / MoE id staging (secondary)

`concat.cu:182-183` two D2D `cudaMemcpyAsync` if both sides packed. `top-k.cu:1280` `Memcpy2DAsync`. `mmvq.cu:1979` ids `Memcpy2DAsync`. `ggml-cuda.cu:2740,2761` **D2H then H2D of expert ids** (host round trip, `cudaStream` compute). Those last two are real host copies; size = `ne_get_rows * 4` bytes, stream compute, sandwiching a host wait.

**Trace ID:** tiny `copyBuffer` (hundreds of bytes) with `MemcpyKind` H2D/D2H if rocprof records it; adjacent `mul_mat_id`. Volume << 1.25M unless ids are copied per expert per token.

### How to classify the 1.25M in rocprofv3 (do this first)

1. Pair each `copyBuffer` with the **next non-copy kernel on the same stream**.
   - next = `quantize_q8_1` → mechanism 1 (mul_mat src1).
   - next = `rms_norm`/`add`/`mul` → mechanism 2 (CONT/CPY).
   - next = `mul_mat_q`/`mul_mat_vec_q` with size in MiB → weight / sched split (3).
2. Histogram sizes. Predicted peaks: 10240 (2560 f32), 20480 (q=2), `GGML_PAD(2560,512)*4=10240` already aligned, 40960 (4-stream HC).
3. Count `copyBufferRect` separately. If Rect ≈ copyBuffer, the src1 layout is row-contiguous not packed.
4. `GGML_SCHED_DEBUG=1` once. If `n_splits==1` and split inputs empty, drop mechanism 3.

If (1) is ~582/token, the fix is **graph-level contiguity of activations**, not the scheduler and not fusion of matmul shapes. Fusion of QKV/gate-up still helps by deleting consumers, but the copy dies only if the remaining consumer’s src1 is packed.

- hipEngine / ROCm issue 6409: four HIP streams **lose** 20× to a barrier-free Vulkan CB on gfx1151 small kernels. Do not expect HIP stream depth to raise busy.
- llama.cpp discussion 17621 (am17an): CUDA fusion + `GGML_CUDA_GRAPH_OPT=1` concurrent streams. NVIDIA; HIP not measured.
- nabe2030 HIP vs Vulkan Strix Halo: `ROCWMMA_FATTN=OFF` pp16384 +157%. Kernel choice, not launch overlap.
- llama.cpp PR 21344 gfx1151 MMQ VGPR: +19–35% prefill (`0xSero/framework-research` phase-0). Compute tile, not busy/span.

Net: the only RDNA-measured way to move busy/span for small kernels, other than graphs, is **delete launches** (fusion / fused consumers / contiguous src1 so the copy+quantize pair disappears). HIP multi-stream is not it (6409).
