## 1. `src1_ddq` reuse across mul_mat ops sharing one src1

**Mainline ggml/llama.cpp: not found** as a cache keyed on the source tensor.
`ggml_cuda_op_mul_mat` still allocates a pool `src1_ddq` and calls `quantize_src1` per op.
Same shape in this tree at `engine/ggml/src/ggml-cuda/ggml-cuda.cu:1867-1880`.
Discussion that confirms the per-op Q8_1 convert, with no reuse proposal:
https://github.com/ggml-org/llama.cpp/discussions/11743

**Closest working implementation: ik_llama.cpp graph-walk, not a keyed cache.**
Live `ggml_cuda_mul_mat_q` on `ikawrakow/ik_llama.cpp` `main` (file fetched 2026-08-25,
https://github.com/ikawrakow/ik_llama.cpp/blob/master/ggml/src/ggml-cuda.cu ):

- Quantize `src1` once into `src1_quantized`.
- Then `while (node_n + 1 < cgraph->n_nodes)`: skip reshape/view/permute; **break** if
  `dst->op != MUL_MAT || dst->src[1] != src1` or types/layouts disagree;
  else dispatch the next mul_mat with the **same** `src1_quantized.get()`.
- Extra QKV-with-bias special case: `mul_mat(Q/K/V) -> add` fused, one quantize for three matmuls.
- MMQ layout guard: `mmq_get_q8_1_ds_layout(src0->type) != mmq_get_q8_1_ds_layout(next->type)` breaks reuse
  (so Q4_K then Q6_K consumers of the same activation cannot share the q8 buffer).

Limitation: only adjacent graph consumers of the identical `src1` pointer. An intervening
RMS/HC Mix/copy breaks the walk. That is reuse, not a tensor-id cache.

**Same diagnosis, different fix: fuse the two consumers so there is only one mul_mat.**

- ik_llama.cpp PR 229, merge `ac1d259` (2025-02-23):
  https://github.com/ikawrakow/ik_llama.cpp/pull/229
  Quote: "up and gate have the same second operand so that, if they are quantized, the quantization is unnecessarily repeated."
  New fused MoE up/gate/act op. CUDA PP +26% / TG +7% on DeepSeek-Lite (RTX 4080).
- llama.cpp PR 19139, merge `b68d751`: `--fuse_gate_up_exps` concatenates gate/up so one `mul_mat_id`.
  https://github.com/ggml-org/llama.cpp/pull/19139
- llama.cpp PR 22780 (`--fuse-qkv`): one MUL_MAT then view-split. Preferred over a gfx1151-only K+V concat
  in llama.cpp discussion 26378 (am17an, 2026-08-01).
  https://github.com/ggml-org/llama.cpp/pull/22780
  https://github.com/ggml-org/llama.cpp/discussions/26378
- llama.cpp PR 13014, merge `658987c` (JohannesGaessler): MMVQ + bs=1 MUL_MAT_ID cuts launches by n_used experts
  and drops a `cudaStreamSynchronize` before launch.
  https://github.com/ggml-org/llama.cpp/pull/13014

**Sizing caveat (matches inbox 172600Z):** reuse only pays where one activation feeds several matmuls.
Fused QKV already quantizes once by construction. Remaining candidates: HC down/up/inject and MoE gate+up.

## 2. HIP launch overhead / GPU-busy on gfx1151

**HIP graph replay stays OFF here.** Local A/B, `engine/CMakeLists.txt:18-66`
(`GGML_HIP_GRAPHS OFF` FORCE after `f026c35` / retest 2026-08-22):

- graphs ON : decode 33.51 tok/s, prefill-128 206.6
- graphs OFF: decode 34.69 tok/s, prefill-128 212.7  (−3.4% / −2.9% with graphs)
- mismatch is `[graph-mismatch] node=0 op=VIEW name=ds4_raw_kv_1`; ring-buffer write offset is baked into the captured VIEW.
- Same diagnosis in lucebox-hub PR 156: "kv_start baked into ggml_view offsets blocks surgical hipGraph".
  https://github.com/Luce-Org/lucebox-hub/pull/156

Generic CUDA-graph advice does **not** override that. gfx1151 measurements of graph replay itself:

**Graph capture is a high floor, not a free lunch, on this silicon.**

- hipEngine / ROCm issue 6409 (lhl, 2026-07-11), matched TheRock 7.15, gfx1151 Radeon 8060S:
  https://github.com/ROCm/legacy-rocm-build/issues/6409
  Warmed 941-node HIP graph: **1.841 µs/node**. Vulkan command-buffer replay of the same serial chain: 0.605 µs/node (3.04×).
  Single tiny dispatch: HIP 6.893 µs vs Vulkan 0.641 µs (10.75×).
  Independent 4-stream small kernels: Vulkan 20.83×–21.02× HIP on gfx1151.
  Evidence commit `e5dbc822`, gfx1151 source `0e566a45`.
- vLLM issue 32180: HIP graph capture on gfx1151 hits a driver timeout; production workaround `--enforce-eager`.
  https://github.com/vllm-project/vllm/issues/32180
- nabe2030 HIP vs Vulkan on Strix Halo, llama.cpp `7b8443ac` / tag b8966, ROCm 7.2.2:
  https://github.com/nabe2030/hip-vs-vulkan-evo-x2
  `GGML_HIP_GRAPHS=ON` on Qwen3.5-35B-A3B Q4_K_M: **no measurable benefit (±1%)**.
  Comment: graphs help launch overhead when kernels are tiny; they do not, when kernels are large.
- AMD-Ecosystem/llama.cpp PR 59 regression board (jeffli-xilinx, 2026-07-20):
  **`GGML_CUDA_DISABLE_GRAPHS=1` required on that gfx1151 board.**
  https://github.com/AMD-Ecosystem/llama.cpp/pull/59

Arithmetic against the TSK 4,455,958 prefill dispatches: even a perfect 1.84 µs/node replay
is ~8.2 s of doorbell time before any compute. Graphs cannot rescue a 2,148-launch-per-token
graph. They only pay after launch count drops by ~100×.

**Techniques that are actually measured on gfx1151 / RDNA3.5:**

1. **Fuse so there are fewer launches** (this is the lever that matches 13.9% busy).
   - AMD-Ecosystem/llama.cpp PR 59: concatenate wk+wv at load so one MMVQ instead of two on gfx1151.
     Occupancy: 40 CUs = 80 SIMDs; N=1024 MMVQ sits at 12.8 waves/SIMD; N=2048 reaches 16.0 (cap).
     **24-VGPR budget; nwarps / rpb / K-split / wave64 all failed by crossing 32 VGPR.**
     E2E tg128 +1–2% on 0.5B–4B, flat on 7B+ (FFN dominates). Kernel already optimal at nwarps=1, rpb=1.
   - AMD-Ecosystem/llama.cpp PR 67 (via discussion 26378): fuse silu/sigmoid / silu*mul / residual-add
     into MMV epilogue. Launches/token 1263 → 1103, ~+1.4% tg128. Not gfx1151-only.
   - ik_llama.cpp PR 229 (above): fused MoE up/gate, one quantize + one barrier instead of three.
   - llama.cpp PR 13014: bs=1 MUL_MAT_ID, launches / n_experts.

2. **Batched / multi-stream submission.**
   Issue 6409: four nonblocking HIP streams lose badly to a barrier-free Vulkan command buffer
   on gfx1151 (20×). Do not expect HIP multi-stream of tiny kernels to hide the 86% idle.
   llama.cpp PR 16991 (`GGML_CUDA_GRAPH_OPT=1`) is NVIDIA stream-concurrency; not gfx1151 evidence.

3. **Persistent kernels / persistent workgroups: not found for gfx1151 LLM prefill/decode.**
   Closest miss: FlyDSL PR 1028 `persistent_wgs` on **gfx1100** RDNA3 GEMM, motivated by ~90 µs host launch;
   NUM_CU hard-coded for gfx1100, author says thresholds do not transfer.
   https://github.com/ROCm/FlyDSL/pull/1028
   netra-kernel `runtime/gfx1151/` does HIP-graph-compatible packed-kernarg launches for mxfp4, with
   graph-node-count and replay p50/p90 in the harness — that is an SGLang plugin, not ggml.
   https://github.com/NetraRuntime/netra-kernel/blob/main/runtime/gfx1151/README.md

**Weighing against HIP-graph-OFF:** do not re-enable `GGML_HIP_GRAPHS` to fix 13.9% busy.
The local mismatch (VIEW offset) plus the 1.84 µs/node HIP replay floor plus vLLM capture hangs
all say: cut `quantize_q8_1` + `copyBuffer` launches first (55% of prefill dispatches), then
consider a **position-independent** graph (indirect index, not baked VIEW) only after the
node count is in the low thousands, not millions.

## 3. MMVQ vs MMQ numerical equivalence; q=1 vs batched

**Published MMVQ-vs-MMQ numerical-equivalence paper/analysis: not found.**
Switch-point PRs are throughput-only (no logit / PPL tables comparing the two kernels on the same batch):

- llama.cpp PR 23227 / release b9387: AMD MFMA MMVQ→MMQ at batch≥4 for K-quants. Explicitly
  "Non-AMD-MFMA paths (NVIDIA, RDNA, CDNA1 without MFMA) are byte-identical to master."
  gfx1151 is RDNA3.5, not MFMA. https://github.com/ggml-org/llama.cpp/pull/23227
- llama.cpp PR 26079: per-HW mvq→MMQ crossover, still a perf patch.

**Known systematic (not noise) ggml quantized-matmul bugs, with scope:**

1. llama.cpp PR 17089, merge `e14e842` (JohannesGaessler, 2025-11-08):
   https://github.com/ggml-org/llama.cpp/pull/17089
   MMQ **stream-k fixup used the wrong `ne1` indices** → PPL jump on MoE.
   GraniteMoe-3B q4_0 RTX 5090: 15.4910 → 10.0853. Same class in ik_llama.cpp PR 913 (`12b9902`).
   **Does not hit gfx1151.** Local `mmq.cu:407-409`:
   `use_stream_k = (NVIDIA && arch>=VOLTA) || CDNA`, and `src1_ncols == ne11`.
   RDNA3.5 is neither.

2. llama.cpp issue 27407 (2026-08-19): greedy output diverges under **batched speculative verification**
   on CUDA. Author classifies it as **near-tie dependent, not systematic**; Metal DFlash2 was byte-identical.
   https://github.com/ggml-org/llama.cpp/issues/27407
   Signature is token flips at near-ties, not 16.4→14.3 top-1 attenuation.

3. hipEngine issue 6409 numerical appendix: **Vulkan** q8_1 `d` scale stored one FP16 code below
   the CPU/HIP oracle (1374/2816 Q4 blocks). Isolated as shader FP16 pack, not HIP MMQ.
   Uploading CPU q8_1 made Vulkan Q4 KL 4.46e-51. **Not a HIP/MMVQ bug.**

4. llama.cpp PR 4801 (JohannesGaessler, closed prototype): int8-tensor-core GEMM with
   **one scale per activation row** vs per-block scales had "precision issues"; workaround was
   15-bit "double precision" int8. Not landed; documents that changing the **scale grouping**
   of q8 activations is numerically load-bearing.
   https://github.com/ggerganov/llama.cpp/pull/4801

5. ik_llama.cpp PR 194: Q8_1 fp16 block-sum overflow on IQ1_S_R4. Different quant, different symptom.

**Batch-wide vs per-row normalization bug in ggml MMVQ/MMQ: not found.**
`quantize_q8_1` is per-block-of-32 warp amax/sum (`ggml-cuda/quantize.cu`), not batch-wide.
MMQ uses a different q8_1 **layout** (`MMQ_Q8_1_DS_LAYOUT_D4 / DS4 / D2S6` in `mmq.cuh`)
than MMVQ's `block_q8_1`. That is per-block grouping, not a batch-wide scale.

**Why this likely is not an MMVQ→MMQ switch at q=2.**
`MMVQ_MAX_BATCH_SIZE` is 8 (`mmvq.cuh:3`). Isolated type-101 drift in the TSK is already tiny
and unbiased (normalized_rms 2.14e-4, mean_error ~1e-7). q=1 and q=2 should still be MMVQ
unless a type-101 path forces MMQ. If both widths use MMVQ, kernel family is not the discriminator.

**Better numerical pin for *this* model, not ggml matmul:** Gated Residual RMS is **per branch**,
not over the concatenated `n*C` vector (see Q4). A batched kernel that RMS-reduces over
4×2560 instead of four 2560-wide streams would systematically attenuate hidden states,
preserve top-1 on a near-tie, and match "cross-kernel drift" better than MMQ stream-k
(which this GPU does not run). Miles states DeepSeek-V4's `learned_output_contract` **must not**
be reused for that reason:
https://miles.radixark.com/docs/models/qwen/qwen3-8-flash-next

## 4. Qwen3.8-Flash-Next numerics pins

Sources, in order: tech report PDF
https://github.com/QwenLM/Qwen3.8-Flash-Next/raw/main/tech_report.pdf
(`On the Design of Qwen3.8-Next Architecture`, Qwen Team, Aug 2026);
HF card https://huggingface.co/Qwen/Qwen3.8-Flash-Next ;
SGLang day-0 https://www.lmsys.org/blog/2026-08-26-qwen-flash-next/ ;
Miles recipe https://miles.radixark.com/docs/models/qwen/qwen3-8-flash-next
(miles#2777 `afd78afd`, Megatron-LM#89 `e8f57451`);
NeMo AutoModel https://docs.nvidia.com/nemo/automodel/model-coverage/large-language-models/qwen/qwen3-8-flash-next

### Shape (HF card, must match kernels)

- 125B backbone, 6B activated/token, +51B n-gram, +4B MTP. Hidden 2560. Vocab 248320 padded.
- 48 layers: `12 × (3 × (GDN → MoE) → 1 × (QSA → MoE))` = 36 GDN + 12 QSA.
- GDN: 48 V heads / 16 QK heads, dim 128.
- QSA: 24 Q / 2 KV, dim 256, RoPE dim 64 (`partial_rotary_factor = 0.25`).
- MoE: 512 experts, top-10 routed + 1 shared, intermediate 640.
- Gated Residual: 4 branches, bottleneck rank 320.

### RMS placement (this is the exactness trap)

- **No block `input_layernorm` / `post_attention_layernorm`.** Checkpoint ships none.
  Each hyper-connection `hc_norm` *is* the pre-block norm. A leftover fused TE norm
  "corrupts the forward pass silently" (Miles §1, §5.5).
- **Zero-centered RMSNorm** retained from Qwen3-Next: weight init 0, `y = (1+γ) * x / rms(x)`;
  last-dim mean only. HF `Qwen3NextRMSNorm` is the same pattern
  (https://github.com/huggingface/transformers/blob/main/src/transformers/models/qwen3_next/modeling_qwen3_next.py).
- **GR, tech report eqs. 29–30:** each of the 4 branches is RMS-normalized **independently**
  with its own `γ_i ∈ R^d`, then an elementwise data-dependent read gate mixes them:
  `GatedNorm(u) = RMSNorm(u) ⊙ σ(W2 SiLU(W1 RMSNorm(u)))` with low-rank W1/W2.
- **Head contraction is not DeepSeek-V4 `learned_output_contract`.** Same low-rank gated mean
  as per-layer HC, **RMS taken per stream, not over the whole `n*C` vector** (Miles; Megatron-LM#89).
- Attention: `--qk-layernorm`, `--apply-layernorm-1p` (Miles). QSA indexer RMS is **on queries only** (below).
- PLE path: `Δ_t = U_t + SiLU(DWConv(RMSNorm(U_t)))` (SGLang).

If a batched prefill RMS reduces over concatenated residual streams or over the token batch
instead of per-row / per-branch, the report's (30) is violated. That is the first place I
would look for systematic attenuation at q=2.

### HC mixer (Mix / Combine)

SGLang + FlashInfer PR 4266. Mix: 4×2560 → 2560 via low-rank gates; Combine: 2560 → 4×2560.

- Mix `M≤16`: split-K fused GEMM, SiLU/sigmoid/gate/reduction in the two GEMM epilogues.
  Weights reordered offline so the four gates reduce inside a tile. Larger M: cuBLAS.
  B300 M=4: 12.36 → 6.03 µs (2.05×).
- Combine large M: one fused kernel, one pass per token row.
  Combine `M≤32`: **split each row along hidden dim** (two kernels) specifically "preserving
  the reference FP32 accumulation order and bitwise-identical outputs."
  M=4: 4.17 → 2.13 µs.

Prefill (M thousands) and q=1 decode (M=1) are **different kernels**. Bit-equality across
those two is not an SGLang invariant; they only claim bitwise identity inside the small-M
Combine split vs its reference. DeepSeek `force_exact_prefill` is the same idea.

Tensor names (kgptalkie teardown of the released checkpoint):
`layers.N.attn_hyper_connection.{hc_norm, block_inject_weight, input_mix_weight_down, input_mix_weight_up}`
and the matching `mlp_hyper_connection.*`, plus a stack-level `hyper_connection_mixer`.
https://kgptalkie.com/tutorials/llm-benchmarking/qwen-3-8-flash-next-vs-qwen-3-8-27b

### PLE (n-gram / Engram)

- One table, **decoder layer 2** (configured layer ID 2 = 0-based index 1). Layer 0 has none.
- 8 bigram hash heads `(x_{t-1}, x_t)` + 8 trigram heads `(x_{t-2}, x_{t-1}, x_t)` → 16 row IDs.
- 160 values/row, concat to `E_t ∈ R^{2560}`.
- Table: 320,001,536 padded rows × 160, 51.2B params, 128 shards (NeMo).
- Injection (SGLang): `E_t → K_t ∈ R^{4×2560}, V_t ∈ R^{2560}`; residual `R_t → Q_t`;
  `g_t = Gate(Norm(Q_t), Norm(K_t)) ∈ R^{4×1}`; `U_t = g_t ⊙ V_t`;
  `Δ_t = U_t + SiLU(DWConv(RMSNorm(U_t)))`; `R̃_t = R_t + Δ_t`; then HC Mix → `h_t`.
- State: last two token IDs + short-conv history `[10240, 9]` (= 4×2560 × 9).
- Frozen, host-resident in Miles/SGLang; skipped in weight-update checks.

NeMo: first four decoder-layer states cosine 0.9998–1.0000 vs HF; Engram delta relative L2 < 0.0063.

### QSA indexer

Tech report (12) + SGLang:

```
q^h_i = RMSNorm(W^h_Q x_i)     # 4 heads, dim 128; RMS on Q only
k_i   = W_K x_i                # 1 shared key head, no RMS before pool
```

- Keys partitioned into non-overlapping blocks of **r=4**, compressed by **FP32 average pool**,
  then **normalized and rotated with the first token's MRoPE**.
- Score: `s_{t,b} = 1/√128  ∑_{h=1}^{4} ReLU(⟨q^I_{t,h}, k̄^I_b⟩)`.
- Keep 512 blocks → 2048 logical tokens + 0–3 tail of the current incomplete block (**≤2051**).
- Compressed keys are **index only**. Softmax/value use original uncompressed K/V.
  Cache size still scales like full attention on the 12 QSA layers; 36 GDN layers are fixed-state.
- Indexers are discrete top-k with **no aux loss / no STE** in the released path (NeMo: frozen).

IndexShare MTP (SGLang): reuse the draft-extend selection for the whole MTP loop; accept length unchanged.
Not a prefill exactness issue.
